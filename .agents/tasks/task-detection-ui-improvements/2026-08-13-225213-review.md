# Per-person emotion tracking and snapshot persistence

This change adds three things to the real-time face detection view: a mode indicator banner that tells the user which capture mode is active, per-person emotion tracking in contador mode (labeling faces as per1, per2, etc. and recording emotion transitions), and persistence for snapshot-mode captures (freeze duration extended to 10 seconds, capture saved to the database with poem). It also brightens the gradient colors for better dark-mode contrast and adds colored left-borders to the detection panel cards.

**Watch for:** The `personEmotionHistory` ref grows unbounded for long-running sessions with many face IDs (confirmed). The snapshot capture doesn't include the image data in the database save even though the user requirement mentions saving "la imagen" (confirmed). The `emotions` column now stores two incompatible JSON shapes depending on mode, which any dashboard query must handle (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Per-person tracking piggybacks on the existing face ID system (`nextFaceIdRef`). When a face's dominant emotion changes, the transition is appended to a `Map<number, PersonEmotionEntry[]>`. Every 5-second auto-save interval in contador mode, the full history for all tracked persons is serialized into the `personEmotions` field of the capture payload. This history is never pruned, so a session running for hours will accumulate large payloads and eventually large database rows.

Snapshot mode now freezes for 10 seconds and fires `saveCapture` with the poem as the message and the detected emotions, but the actual JPEG image (`snapshotImage` state) is not included in the payload sent to `/api/captures`. The user asked to save "la imagen, la detección y el poema", but only the detection and poem reach the database.

The API route conditionally wraps the `emotions` array into a `{ detectedEmotions, personEmotions }` object when `personEmotions` is present, meaning the `emotions` jsonb column now holds either `string[]` or `{ detectedEmotions: string[], personEmotions: [...] }`. Any code reading this column (dashboard, GET endpoint consumers) must discriminate between the two shapes.

<details>
<summary>Issues (5)</summary>

1. **Unbounded emotion history** — `personEmotionHistoryRef` is never cleared or truncated. For long sessions, the Map grows without bound and the serialized payload becomes increasingly large. Add a cap (e.g., last N entries per person) or flush-and-reset after each save.
2. **Snapshot image not persisted** — `triggerSnapshot` calls `captureVideoSnapshot()` and stores the result in state for display, but the `saveCapture` call doesn't include the image data. The requirement asks to save the image alongside the detection and poem.
3. **Polymorphic emotions column** — The `emotions` jsonb column now stores two different shapes depending on whether `personEmotions` is present. Dashboard queries and any downstream consumer must handle both. Consider a separate column for the enriched data or a consistent wrapper shape.
4. **Face ID to detection index coupling** — `faceIds[idx]` is used to look up `faces[idx]`, assuming the arrays are in the same order. `updateTracking` returns IDs in the order faces are matched/created, which currently mirrors the input order, but any future reordering of `faces` (e.g., sorting by confidence) would silently break the per-person assignment.
5. **Missing personEmotions validation** — The API route destructures `personEmotions` from the request body and passes it directly into the database without any shape validation. A malformed payload could insert arbitrary JSON into the column.

## Unbounded per-person history accumulation

The `personEmotionHistoryRef` Map accumulates every emotion transition for every tracked face ID across the entire session lifetime. The only time entries are added is when a face's emotion changes; they are never removed. The Map is serialized in full on every 5-second capture save:

```typescript
personEmotionHistoryRef.current.forEach((emotions, personId) => {
  personEmotions.push({
    personId: `per${personId}`,
    emotions,  // entire history array
  });
});
```

Since `nextFaceIdRef` increments monotonically and is never reset (even after faces disappear and the tracked array is pruned), a busy environment where faces appear and leave will accumulate entries for person IDs that no longer exist on screen. After an hour with moderate traffic, this could mean hundreds of entries across dozens of person IDs, all serialized into each capture POST body and stored in the database row.

The fix is either to flush the history after each save (reset the Map after building `personEmotions`), or to cap the history at the last N entries per person, or both.

## Snapshot image omitted from database save

The `triggerSnapshot` function captures a JPEG via `captureVideoSnapshot()` and stores it in component state (`setSnapshotImage(image)`) for display in the overlay. The subsequent `saveCapture` call builds a `CaptureData` object with `eventName`, `personCount`, `emotions`, `dominantEmotion`, and the poem as `message` — but not the image:

```typescript
const captureData: CaptureData = {
  eventName,
  personCount: faces.length,
  emotions,
  dominantEmotion: dominant,
  message: poem,
};
saveCapture(captureData);
```

The `CaptureData` interface doesn't have an image field. The database schema has no column for image storage. Implementing this would require either adding a `text` column for base64 data (simple but expensive for storage/queries) or uploading the JPEG to object storage and storing a URL reference.

## Polymorphic `emotions` column shape

Before this change, the `emotions` jsonb column always stored a flat array of emotion strings: `["happy", "sad", "neutral"]`. After this change, when `personEmotions` is present the column stores:

```json
{
  "detectedEmotions": ["happy", "sad"],
  "personEmotions": [
    { "personId": "per1", "emotions": [{ "emotion": "happy", "timestamp": "..." }] }
  ]
}
```

The GET endpoint returns rows as-is without normalization. Any dashboard component parsing the `emotions` field must now check whether it's an array or an object. This is a schema migration concern — existing rows have the old shape, new contador-mode rows have the new shape, and new snapshot-mode rows still have the old shape.

## Face ID index coupling assumption

In the detection loop, after calling `updateTracking(faces)` which returns `faceIds`, the code does:

```typescript
faceIds.forEach((id, idx) => {
  const currentEmotion = faces[idx]?.emotion;
  ...
});
```

This assumes `faceIds[i]` corresponds to `faces[i]`. Today that holds because `updateTracking` iterates `faces` in order and builds the result array in the same order. The coupling is implicit — if `updateTracking` ever sorts or reorders internally, the per-person assignment would silently map the wrong emotion to the wrong person. The same assumption applies to the UI rendering (`currentFaceIds[i]` paired with `detectedFaces[i]`).
