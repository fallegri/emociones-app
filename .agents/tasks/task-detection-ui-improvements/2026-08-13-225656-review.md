## High-level view

All five issues from the first review are resolved. The emotion history ref flushes after each save cycle. Snapshot images persist in a dedicated `snapshot_image` text column. The schema uses separate columns for flat emotions and per-person data (no polymorphism). Face-ID/index coupling is documented. `personEmotions` is validated before insertion.

The remaining concern is operational: storing raw base64 images in PostgreSQL will cause pain at scale. The dashboard GET returns full rows — including the image column — so every dashboard load transfers accumulated image data unnecessarily. This warrants a follow-up to exclude `snapshot_image` from list queries or move to object storage.

The per-person emotion data (`person_emotions` column) is persisted but never read back anywhere. The feature is write-only until the dashboard consumes it.

## Snapshot image storage and query impact

The `triggerSnapshot` function captures the video frame via `captureVideoSnapshot()` which exports as JPEG at 0.85 quality:

```typescript
return tempCanvas.toDataURL("image/jpeg", 0.85);
```

This base64 string (typically 50-150KB for a 720×560 frame) is stored in the `snapshot_image TEXT` column. The problem surfaces on read. Both `/api/captures` (GET, limit 50) and `/api/dashboard` (recentCaptures limit 20) select full rows:

```typescript
const captures = await db
  .select()
  .from(emotionCaptures)
  .orderBy(desc(emotionCaptures.capturedAt))
  .limit(50);
```

If 20 of those rows have snapshot images, the response could be 2-3MB of JSON. The fix is straightforward: use a column projection that excludes `snapshotImage` in list endpoints, and offer a separate endpoint to fetch the image for a specific capture.

## Validation gap on snapshotImage

The API route validates `personEmotions` shape rigorously but applies no validation to `snapshotImage` beyond the falsy check (`snapshotImage || null`). Any string value — including an arbitrarily large one — will be stored. The endpoint is publicly accessible, and a crafted POST could store an arbitrarily large string. A reasonable mitigation: check that `snapshotImage` starts with `data:image/jpeg;base64,` and is under a size threshold (e.g., 500KB base64 characters).
