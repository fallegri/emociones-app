# Multi-provider AI message generation — re-review after fixes

All five issues from the v1 review have been addressed. The API key transit concern was acknowledged as a known limitation with a documented comment. The stale closure was fixed with a `currentMessageRef` that syncs via a dedicated effect. The detection loop dependency array no longer includes `currentMessage`, preventing effect restarts. Prompt injection is mitigated by `sanitizeEventName` (truncation + control-char stripping) and system/user message separation. Both server-side routes now pass `AbortSignal.timeout(10_000)` to the OpenAI SDK.

Watch for: No new blocking concerns.

**Verdict**: APPROVED

## High-level view

The stale-closure fix uses a `useRef` kept in sync with state through a small `useEffect`, and the detection loop reads `currentMessageRef.current` at capture time. The dependency array is now `[isModelLoaded, eventName, saveCapture, aiConfig, generateAIMessage]` — stable references that only change on meaningful prop/config shifts.

The prompt injection fix applies two layers: `sanitizeEventName` strips control characters and truncates to 100 chars, and the prompt itself separates system instructions (role: "system") from user-provided context (role: "user"). The event name no longer lives inside the instruction payload.

The timeout fix is consistent across both routes — `AbortSignal.timeout(10_000)` is passed as a request option to the OpenAI SDK, which will abort the HTTP call after 10 seconds regardless of provider responsiveness.

## Fix verification: stale closure and effect stability

The `currentMessageRef` is declared alongside the other refs and synchronized through a dedicated effect:

```typescript
const currentMessageRef = useRef<string>("");

useEffect(() => {
  currentMessageRef.current = currentMessage;
}, [currentMessage]);
```

Inside the detection loop, the capture path reads from the ref:

```typescript
message: currentMessageRef.current,
```

When `generateAIMessage` resolves asynchronously and updates state after the 5-second capture window fires, the ref already holds the latest AI response. The static-message path also writes to both state and ref simultaneously, keeping them in sync regardless of which branch executes.

## Fix verification: prompt injection mitigation

```typescript
function sanitizeEventName(name: string): string {
  return name
    .slice(0, 100)
    .replace(/[\x00-\x1f\x7f-\x9f]/g, "")
    .trim();
}
```

Combined with system/user message separation, the user-supplied event name is now in the "user" role message while all behavioral instructions are in the "system" role. An attacker can still put adversarial text in the event name field, but the model treats it as user content rather than instruction — the standard mitigation for this class of issue in non-safety-critical applications.

## Fix verification: AI call timeout

Both routes pass `AbortSignal.timeout(10_000)` as a request option. The `AbortSignal.timeout` API requires Node 18+; Next.js 16 requires Node 20+, so compatibility is not a concern. The 10-second ceiling prevents stacking pending connections under the 5-second AI throttle interval.
